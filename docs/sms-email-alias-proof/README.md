# LuxeGlow SMS signup / email alias proof

This directory preserves the earlier isolated login proof for review. Its code and tests are **not the current implementation**. The staged implementation is in `supabase/migrations/20261027010000_sms_customer_activation.sql`, `supabase/functions/login-rate-limit`, `supabase/functions/claim-sms-signup`, `supabase/functions/send-unisms-sms`, and the frontend files. This checkout starts from the release tree that includes the deployed welcome migration `20261027000000`; no production deployment or SMS send has been made. Run `node gateway.test.mjs` only to inspect the original proof's assumptions; some details below (including alias expiry) differ from the staged migration and need security review before activation.

## Requested user flow

1. Collect email, password, name and mobile number in the same signup form. Treat the email as a **login alias, not verified contact or recovery identity**.
2. Create a Supabase phone/password account with SMS confirmation enabled. A Supabase Send SMS Hook sends its OTP through UniSMS. The browser enters the code through `verifyOtp({ phone, token, type: 'sms' })`. No signup email is sent.
3. On successful phone verification, atomically reserve the email alias against both pending aliases and existing Auth email identities. Activate the customer access gate. The first session comes from the SMS verification. Normal UI sign-in afterward accepts email and password; the server gateway resolves an unverified alias to the verified phone identity and asks Supabase Auth to check the password. Existing verified-email customers and staff continue through their email Auth grant.
4. Offer a separate, optional **verify recovery email** action after signup. Attach the address through Supabase's normal email-change/confirmation flow; only confirmed `auth.users.email_confirmed_at` enables password recovery and outbound account-sensitive email. The address typed at signup is never marked confirmed by SMS.

## Security boundaries required before production

- Create a service-only alias table with `email_normalized` unique, `auth_user_id` unique, `phone_e164`, `expires_at`, `email_verified_at` and `recovery_email_verified_at`. The alias must never be a public profile field. A database transaction must check conflicts with `auth.users` email identities and reserve the alias. Add a Before User Created hook or equivalent check so a direct email signup cannot race or collide with a reserved alias; handle staff invites explicitly. Expire or reclaim unverified aliases by a documented support flow without disclosing whether an email is registered.
- Restrict the gateway to the trusted server, retain the existing hashed email+IP and IP rate limits, send the phone/password request to Supabase Auth with trusted IP forwarding, and return generic failures. Never log plaintext passwords, OTPs, phone mappings, API secrets or provider responses containing sensitive values. Require returned `user.id` to equal alias owner, reread authoritative phone confirmation and active customer status, and recheck the alias before returning a session. Existing/staff email grant remains unchanged.
- On phone change, update the alias phone binding only after Supabase confirms the new number. Invalidate outstanding sessions or enforce the current confirmed number in every customer data gate. Prevent direct `profiles.phone` edits from changing verification state. Unique phone ownership is Auth's responsibility; normalize `+63` numbers consistently.
- Add a `customer_has_verified_phone()` database helper based on `auth.users.phone_confirmed_at` and current `auth.users.phone`, with an explicit grandfather policy for existing customers. Apply it to all private customer RLS policies and every customer `SECURITY DEFINER` RPC, including booking, reschedule, cancellation and review. Direct Auth phone/password access cannot be disabled merely by hiding that UI, so it must face the same database gate. The helper must not trust editable user metadata or `profiles.phone` alone.
- Treat missing or unverified email as ineligible for email delivery. Reconcile the deployed `20261027000000` welcome migration and notification worker before changing any welcome/outbox behavior. Keep email password recovery available only for independently confirmed addresses. Do not globally disable email confirmation or set `email_confirm=true` from SMS proof.
- Supabase limits SMS sends and verification by project/IP; add server-side per-number and project-wide send budgets, CAPTCHA, a short OTP expiry, provider 429 handling, and a kill switch. The UI should give a useful unsupported-number or delivery error without a prominent carrier banner. A prefix cannot prove a ported number's current network.

## Staging acceptance tests

Run with synthetic accounts and a mock UniSMS hook first: successful signup, wrong/expired/reused code, resend limits, provider outage, duplicate/ported number, email alias conflict and race, absent/incorrect password, phone change, alias expiry, unverified recovery denial, verified recovery, and existing customer/staff login. Call Supabase Auth and PostgREST directly to prove unverified accounts cannot access private data or execute booking RPCs. Confirm old welcome and notification behavior against the deployed releases. A real SMS test, secret insertion, Auth hook change, migration and frontend deployment require later authorization and a controlled recipient/credit cap.

`node gateway.test.mjs` runs the proof's synthetic tests.
