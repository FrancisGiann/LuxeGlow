Reversing SQL alone is not a complete rollback for changed Auth users.

## Unresolved before activation

- Staging has no deployed `password-recovery` or `send-unisms-sms` function, so reset-only grants, delivery and provider failure remain unverified at runtime. Do not turn on recovery flags from local tests alone.
- UniSMS's current SMS API documentation says the account-assigned sender is for testing and that a sender ID should be applied for after testing to continue. Its student guide names `Unisoft` as the default testing sender, limited to Globe and DITO. This **controlled defense/demo** scope fits the published testing use; do not treat it as approval for unrestricted customer signup or claim a custom LuxeGlow sender. Sources: https://unismsapi.com/docs/sms and https://unismsapi.com/docs/students.
- Native verified-email recovery and staff invitation behavior must be checked with the access-token hook; preserve existing staff access and Resend Auth SMTP. The existing frontend blocks its own native customer reset when custom recovery is enabled, but callers can use Auth APIs directly.
- The unverified email alias can be reserved by a phone owner who does not own that inbox. Define an audited support correction/dispute path that never transfers the phone owner's account based on inbox proof alone; do not require an email confirmation step during signup.
- Production has no managed backup, and no production UniSMS key, Hook, Phone Auth, SMS migrations, or public flag has been installed. Browser policy requires the owner to enter any new credential directly and requires action-time approval for changing security-sensitive Auth access and sending a paid/credit-consuming SMS.
